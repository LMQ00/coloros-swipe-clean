## 0. 这是什么

ColorOS / realme UI 的 LSPosed 模块（Kotlin）：让用户按应用选择「最近任务划卡（recents swipe）时进程保留还是强制结束」，覆盖系统内置白名单。**应用分身（多开）可单独设置**——分身是独立 user，与本体各自独立。

|---|---|
| 仓库 / 分支 | `LMQ00/coloros-swipe-clean`，`main` |
| 当前版本 | `versionCode 3` / `versionName 1.2`（`app/build.gradle.kts`） |
| 最新 Release | `v1.2` → 提交 `3f90917`，附件 `swipe-clean-v1.2.apk` |
| 构建 | GitHub Actions `.github/workflows/build.yml`；**本机不构建**（Termux/aarch64 无 Android SDK、无 `aapt2`） |
| 测试设备 | realme UI / ColorOS 16（Android 16），root（KernelSU），LSPosed `v2.1.1-it` |
| 逆向目标 | Athena 6.0.1（`versionCode 601`，构建提交 `62c260e`），素材 md5 `60944a5ffc5afb6d393a5ea52d77d90c` |

### 1.4 五个 Hook 点（改之前必须知道挂在哪）

| # | 类 | 方法 | 作用 |
|---|---|---|---|
| 1 | `com.android.server.wm.OplusAthenaManager` | `getRemoveTaskFilterType(WindowProcessController)` | 返回 `1` = 不杀、`3` = 强制杀 |
| 2 | `com.android.server.wm.ActivityTaskSupervisorExtImpl` | 同上 | 唯一调用点，保证拦到 |
| 3 | `com.oplus.athena.common.parser.athena.FilterHelper` | `getStopTypeInner(ProcDetailInfo, r0.a)` | 返回 `0` = 保留（覆盖内存清理等其它调用方） |
| 4 | `com.oplus.athena.systemservice.action.prockill.clear.v` | `D0(t, h, r0.a, ClearRecord, ProcDetailInfo)` | 划卡决策点：保留→跳过；必杀→调 athena force-stop 后跳过 |
| 5 | `com.android.server.am.OplusAppStartupManager` | `shouldPreventStartProvider(ProcessRecord, ContentProviderRecord, ApplicationInfo, String, int)` | 仅当目标包名 == 本模块且厂商原本要拦 → 返回 `false` |

框架侧返回值语义（`ActivityTaskSupervisor` 分支）：`0` 杀但持有 foreground service 时保留、`1` 包级白名单不杀、`2` 进程级白名单不杀、`3` 强制杀。详见 `athena-reverse.md`。

### 步骤 5：划卡实测（**必须真划卡**）

```bash

su -c 'logcat -b events -d' | grep -a -E "am_kill" | grep -a pinduoduo
```

判据（实测样本 `com.xunmeng.pinduoduo`，本体 + 分身 998/999）：

- 不杀：`athena swipe keep: <pkg>#<userId>` / `swipe-up keep: …`，进程仍在

## 5. 坑与注意事项

### 编译期（已被 CI 打回三次）

| 坑 | 原因 / 替代 |
|---|---|
| `Bundle#putStringSet/getStringSet` | 不是公开 API，CI 的 `android-36/android.jar` 里没有 → 用 `putStringArray/getStringArray` |
| `UserHandle#of/getUserId/myUserId/getIdentifier` | 同上 → 用 `uid / PER_USER_RANGE`；需要 `UserHandle` 实例时只能用 `LauncherApps#getProfiles()` 给的 |
| `Process#SYSTEM_UID` | 同上 → 写死字面量 `1000` |
| `LauncherUserInfo#getUserSerialNumber()` 返回 `Int` | 不是 Long，比较前 `?.toLong()` |
| `runCatching{…}.getOrDefault(-1L)` 类型推断 | 会被推成 `Nothing` → 用显式类型或 `getOrNull()` |
| `compileSdk` 必须是 36 | libxposed `api` 制品声明 `minCompileSdk=36`（`targetSdk` 仍 35） |
| Kotlin 必须 ≥ 2.2 | 低版本在该 classpath 下触发 FIR 崩溃（`FirIncompatibleClassTypeChecker`） |
| 已验证公开可用 | `LauncherActivityInfo#getBadgedIcon(int)`、`LauncherApps#getProfiles/getActivityList/getLauncherUserInfo`、`UserManager#getUserProfiles`、`SharedPreferences#getStringSet` |

### 运行时 / 系统行为

| 坑 | 说明 |
|---|---|
| LSPosed 作用域必须是**进程名 `system`**，不是包名 `android` | 两者在 UI 里都显示「Android 系统」；选错表现为「模块已启用但完全没有日志」 |
| `onSystemServerStarting` 早于 AMS 就绪 | 此时注册接收器与 `resolver.call()` 都会 NPE，**必须**带重试（`ConfigBridge.install` 的 1s×30 + 5s×60） |
| ColorOS 会拦第三方 App 的 provider 冷启动 | 即使 caller 是 uid 1000；`AppStartupHooks` 只对本模块放行，**不得**放宽到其它包 |
| 开机窗口内 ColorOS 还会拦第三方 App 启动 | 闸门是 `OplusAppStartupManager#isPreventBootStartData()`（`OplusAppStartupManager.java:4082`，默认 30s，名单 `BOOT_PREVENT_START_APPLIST`），**不在 Hook 5 覆盖范围**。实测完整重启后启动期拉取全部失败，直到用户打开一次 App 才成功（**不是等固定时长就放行**——本会话曾误判为「约 5 分钟」，实为用户恰好那时打开了 App）；靠 `ConfigBridge` 的开机缓存绕过 |
| 名单 key 必须带 userId | 分身 userId 实测有 998、999 多个值，**不得硬编码** |
| 不介入 athena 的 `G0`/`J0` | `J0` 已同时比较 `pkgName` 与 `userId`（`v.java:245`），同包名不同 user 互不影响 |
| 必杀路径不要改 | 走 athena `utils.p.b` force-stop 已实测有效；改成模块侧直调 `forceStopPackageAsUser` 属未验证路径 |
| LSPosed 的 modules 日志**会丢行** | 实测 `12:28:14` 的 `config loaded` / `config bridge ready` 未落盘（同线程更早的行在）。判断状态别只看日志，用 `dumpsys activity providers|broadcasts` + 缓存文件 mtime 交叉验证 |
| 无法伪造划卡 | 清理请求 caller 限定 `com.oplus.recents`，必须手动划 |
| `uiautomator dump` 在本 ROM 不可用 | rc=1 且无输出；截图用 `screencap -p`，且**输出必须写到 `~/tmp`**（`/data/local/tmp` 对 Termux uid 不可写） |
| 手机息屏（`Dozing`）时 `input`/截图无效；`NotificationShade` 会抢焦点 | 做 UI 自动化前先确认亮屏且没有下拉通知 |
| 本机到 GitHub 间歇不可用 | push / `gh run download` 要带重试循环 |
| 重启会杀掉 Termux/omp 会话 | 定时重启用 `nohup sh -c "sleep N; setprop ctl.restart zygote" &`，取消要按 pid `kill -9`（`pkill -f "sleep N"` 不可靠） |
| 配置的单一真相来源是 App 的 `shared_prefs/config.xml` | `/data/system/swipeclean_config.json` 只是 Hook 侧副本；App 卸载后缓存仍在，模块会继续按最后一次名单执行 |
| 本机不执行构建 | Termux/aarch64 无 Android SDK、无 `aapt2` |

## 6. 未做的事 / 已知缺口

**功能覆盖缺口**（都是设计内的已知限制，不是 bug）：

- **系统应用不受名单控制**：`G0()` 把 `procDetailInfo.system == true` 的应用交给 `I0()` 分支；UI 默认不显示系统应用
- **最近任务里手动锁定过的卡片**不受控制（`aVar.e()` / `O0()` 的锁）
- **同一 userId 下**同包多任务：athena `J0` 跳过，模块不介入
- **无 launcher 入口的分身应用**不列出（分身枚举走 `LauncherApps#getActivityList`，只覆盖带 `MAIN`/`LAUNCHER` 的包）

**未实现**：

- **模块 App 开机自动启动**未做：ColorOS 的开机窗口闸门（`isPreventBootStartData` / `BOOT_PREVENT_START_APPLIST`）**实际调用点未定位** `[待确认]`。当前用 Hook 侧缓存绕过，功能上不受影响
- **没有任何自动化测试**：仓库无 test 目录，验证靠 CI 构建 + 真机日志。改动判定逻辑时只能靠 §4 步骤 5 的真机划卡
- **两个临时探针 commit 仍在历史里**：`efd4e68`、`c3f7d09`（内容已被 `0fbc4b5` 移除）。未 squash，需 force-push，尚未决定

**未验证 / 边界**：

- `docs/athena-reverse.md` 的全部结论只对 Athena 6.0.1（md5 `60944a5ffc5afb6d393a5ea52d77d90c`）成立。同目录的 `Athena_6.0.1.apk`（md5 `01599ff8…`）是**另一个混淆构建**，结论不可混用
- 分身序号按 `userSerialNumber` 升序排名，实测 999→1、998→2（与 ROM 角标一致）。换 ROM / 换设备是否仍成立 `[待确认]`；取不到序号时 UI 退回显示 `#<userId>`
